# Agensh → TheoremOS 吸收计划

日期：2026-10-23，更新：2026-10-24。状态：已实施离线 module 切片 1–3，并接入成果流诊断；真实模型对照继续暂停，Lead 故障收尾保留证据门槛。

具体 interface、状态所有者、seam 与测试方式见 [module 设计](agensh-module-design.md)。

本轮已集中职责 assessment，接入真实派发分支的等待观察、归档和 inspect，并调整新 helper 的共享归属指示。已有 handoff 完整发布与 CAS 路径继续复用。历史运行基线及无法确定的耗时见 [离线基线](agensh-offline-baseline.md)；这些变更验证流程能力，尚无真实解题收益结论。

成果流的高层 interface 为 `inspectStoredRun(run, options?)`。普通 inspect 同时展示存档成果与显式指定日志中的逐次观察，`--batch` / `--log` 补充日志来源；缺失或冲突保留 unknown / ambiguous。任务改版、重复决定和条件证明单独保留，续跑来源只读取本运行冻结附件。实现与证据口径见 [module 设计](agensh-module-design.md) 和[用法](usage.md#5-查看研究状态与修改计划)。阶段一所需的真实成果交接样本仍待后续获准的新运行，fixture 只验证可观测性。

目标是缩短“研究发现 → 可执行引理 → 独立验证 → 消费者使用 → 原目标闭合”的路径，减少已有可用工作因归属或规划交接而等待。吸收 Agensh 的持续协作与成果流动经验，沿用 TheoremOS 的精确数学合同和验收体系。

Agensh 的大规模结果主要支持固定墙钟下增加并行投入的可行性；论文没有等总 token 的独立并行或中心式编排对照。本计划将协作收益作为待验证假设，不预设扩容一定提高成功率。

**现有基础与本次增量**

| 已有能力 | 本计划关注的增量 |
| --- | --- |
| 独立异步 worker、M3 就绪选择、M5 共享分配、隔离 worktree | 减少未启动任务不必要的 owner 绑定 |
| 回合内研究交付、实时通知、完整事件与 CAS 计划发布 | 缩短发现到 handoff 决策及首次执行的等待 |
| 精确类型、消费者接口、条件连接检查、AND/OR 证明路线 | 让已有检查结果更直接影响任务供给与优先级 |
| 固定快照检查、声明级合并、Lean 回执、独立 S3 | 在这些边界内评估 Lead 故障后的有限收尾 |
| 共享预算、恢复、inspect、三组比较和模块实验工具 | 复用记录定位瓶颈，分开测量组织方式与规模收益 |

实施继续遵守 [模块边界](solver-modules.md) 和 [协作证明协议](cooperative-proof-routes.md)：原题及环境冻结、assignment 与依赖版本绑定、writer 停止后冻结源码、恢复后重新取得有效检查证据。条件证明与研究结论不替代无条件证明，原目标成功只由匹配的 S3 决定。

工作保持在现有独立 CLI 与 M1–M5 内，不增加 Team 服务、聊天服务或新的编排层。当前工作树含其他进行中的修改；开始实施时重新确认现状，以固定源码、构建和模块身份建立基线，不把这些修改的效果归因于本计划。

**阶段一：定位协作等待，建立可比较的基线**

先复用现有 inspect、事件和归档，回答三个问题：有多少工作因 owner 绑定而等待；研究成果在哪个交接环节等待；Lead 不可用是否实际损失了可完成的工作。

1. 串联已有任务版本、assignment、delivery、handoff 决策、检查与集成事件，分别记录发现到决策、采纳到首次执行、ready 到冻结检查、检查到集成的耗时。消费者使用以实际检查引用为依据，模型报告的使用单列。
2. 复用 worker 的 working/preparing/idle/stopped 状态、dispatchCounts、integration queue waitedMs 和 obligation progress。只有无法回答上述问题时，才在现有报告或事件上补最小字段。
3. 区分等待 Lead、owner 限制、依赖未完成、验证/集成、预算限制及没有独立工作。旧记录不足以确定原因或时长时标记未知，不从最终状态倒推全过程。

交付：基线报告、指标口径及确有必要的最小记录补充。没有真实历史证据的场景用可丢弃 fixture 检查可观测性，并明确标为模拟。

完成条件：能从原始记录解释至少一个“有任务却未派发”的场景及一个成果交接场景；缺失记录可见；任务数量、消息数量和 worker 忙碌程度不被计为数学进展。

主要入口：[inspection.ts](../src/solver/inspection.ts)、[archive.ts](../src/solver/archive.ts)、[cooperationCore.ts](../src/solver/cooperationCore.ts)、[cooperationIntegration.ts](../src/solver/cooperationIntegration.ts)。

**阶段二：让现有工作更容易被领取和消费**

优先做这一阶段。共享领取、handoff 发布和消费者连接机制已经存在，先调整任务供应和使用策略，避免重建调度器。

| 工作项 | 拟做工作 | 完成条件 |
| --- | --- | --- |
| 未启动引理共享领取 | 对新建、未开始且无需专属上下文的 helper，规划优先省略 ownerId；保留显式用户归属、已有 assignment、指定 Engineer 和审阅独立性。删除 ownerId 不释放已有 assignment | 在原 owner 忙碌、另一合格 worker 空闲的场景，共享任务可直接领取；专属和已分配任务仍受约束 |
| 核验 handoff 及时使用 | 回合内发布、提示与 CAS 已实现，先测量提案到决定及派发的等待；仅在发现具体瓶颈后调整批次选择或上下文呈现。每次发布仍完整决定本轮展示的请求，未展示和晚到项继续保留 | 现有回合内发布路径得到验证；迟到、重复或过期事件不能改写当前图；没有可测瓶颈时不增加新行为 |
| 优先消费有效成果 | 先比较已有 plan / continuation 策略；围绕当前原目标前沿使用已检查引理，并及早检查昂贵引理的消费者连接 | 能展示消费者实际使用及原目标未闭合前沿的变化；仅有条件连接成功时仍显示输入欠缺 |

这些变更逐项冻结版本和比较，不将共享归属、上下文及排序同时变化后归因于某一项。Lead 仍负责正式任务图与数学路线决策，host 不自动采纳任意研究提案。

阶段验证复用现有回归，只为新行为补充缺口，覆盖：忙碌 owner 与空闲 peer；同时领取竞争；已有 assignment 不迁移；私有范围与审阅独立性；CAS 冲突和重复发布；新旧提案并存；连接成功但引理未证；恢复后的证据重验。

交付：每项实际变更、对应回归和使用说明，以及阶段一口径下的等待变化。离线回归只能证明流程行为，解题收益留待阶段四判断。

主要入口：[organization.ts](../src/solver/modules/organization.ts)、[context.ts](../src/solver/modules/context.ts)、[cooperationInputs.ts](../src/solver/cooperationInputs.ts)、[handoffPublication.ts](../src/solver/handoffPublication.ts)、[taskConnections.ts](../src/solver/taskConnections.ts)。

**阶段三：评估 Lead 故障后的有限收尾**

仅在基线或明确故障场景显示团队级中止会损失有效成果时实施。当前 Lead 存活是后续派发的条件，Lead 的部分终止错误也会触发全队 abort；这与它不主持每项日常派发并不矛盾。

第一版只考虑：Lead 的模型/会话故障经现有重试仍无法恢复，而其余 worker、运行锁、固定任务合同、预算和 verifier 均有效。

1. 故障发生时立即暂停规划和新派发，记录当时模型回合已启动的 assignment 集合；仅预留、已领取或正在打开会话的工作不得启动。确认故障 Lead 的受管 writer 停止并封存其派发后，才允许后续 canonical 操作；不自动产生新 Lead。
2. 仅上述集合内且合同仍有效的工作，可以在既有预算内完成当轮，走到交付、停写、冻结、检查与归档边界，不续派下一轮。有限收尾期限取已有本轮期限与求解期限的较早者；两者均无限时，首版保持当前中止行为。到期沿用停止、草稿保存与 writer 隔离规则。
3. 区分 Lead 服务故障与用户停止、运行锁丢失、验证器不可用、writer 无法确认停止等情形。后几类沿用各自停止与隔离规则；收尾不增加请求额度，不绕过最终审阅或 S3。
4. 恢复沿用现有 thread/checkpoint 与身份检查。收尾期间保存的成果在恢复时按精确版本重新核验，避免重复派发和集成；需要新路线、新假设或新任务图时，等待规划职责恢复。

完成条件：故障注入能保留符合合同的成果，且能区分已启动与仅预留任务；用户停止、期限到达与锁失效仍阻止相应工作；合同变更使迟到产物失效；条件证明不升级为无条件证明，缺少完整原目标及所需审阅时不能报告最终成功。

交付：明确的暂停/收尾/恢复语义及端到端故障回归。若无法在现有生命周期内保持这些约束，保留当前中止行为并记录原因，不先扩大容错范围。

主要入口：[research.ts](../src/solver/research.ts)、[cooperation.ts](../src/solver/cooperation.ts)、[workerProofLifecycle.ts](../src/solver/workerProofLifecycle.ts)、[evaluation.ts](../src/solver/evaluation.ts)。

**阶段四：用对照决定是否扩大投入**

真实模型调用沿用 [当前暂停约定](../examples/components/EXPERIMENTS.md)。本次不启动校准、实验或旧运行；先写好冻结配置与报告口径，后续执行时使用新的隔离运行。

先在固定四人协作配置下，逐项比较阶段二策略与默认策略，再研究规模。阶段三主要通过故障场景检验，不与普通解题策略混在一起归因。

| 比较 | 固定内容 | 回答的问题 |
| --- | --- | --- |
| single / independent / cooperative | 相同题目、模型与推理配置、环境、工具和最终评测 | 协作是否比独立搜索带来额外收益？ |
| 固定墙钟 | 相同求解时间限制，记录实际请求与 token | 并行是否更快产生原目标证明，消耗多少？ |
| 共享上报 token 额度 | 相同服务商上报额度，记录超额、缺失与时间限制 | 在可观测预算条件下，协作是否提高有效产出？ |
| 2 / 4 / 8 workers | 每个规模明确角色组成、路线并发与其余配置 | 当前任务宽度能否有效利用更大工作池？ |

规模比较使用普通三组工具：single 臂为一人，independent/cooperative 使用所选的 2、4 或 8 人；不是用 workers=1 启动所有组。模块替换实验先固定四人。默认角色组成随规模变化，因此人数比较也包含组织配置变化，不能称为纯人数效应。

服务商上报额度不是精确等 token 或计费上限，已发请求可能超额；完整用量缺失时保留未知。预算须先单独校准到能够覆盖规划、证明和验收，不能把全组停在规划阶段解释为证明策略差异。

题目复用现有 IMO2026 或 PutnamBench 适配与比较入口。先用已有兼容样本检查流程，再按预算预先固定扩展题集、重复数及采用标准；小样本结果只报告探索性信号。不同来源、模型、预算或构建的结果分开统计，所有计划尝试及失败都保留。

| 指标层次 | 报告内容 |
| --- | --- |
| 主要结果 | 匹配的原目标 S3 验收数/计划尝试数、达到最终验收的求解耗时、实际 token 与记录完整性 |
| 成果消费 | 无条件引理被实际消费者引用、原目标未闭合前沿变化；条件连接与模型报告单列 |
| 协作成本 | handoff 及领取等待、验证与集成等待、相同输入下的重复探索、规划/证明/审阅用量 |
| 运行质量 | 主动取消、故障、不完整、缺失、预算超额和恢复情况；本地评测与 official 状态分开 |

复用已有 accepted/planned、solveWallMs、wallMs、dispatchCounts、usage 和错误报告；精确阶段延迟仅补必要聚合。solveWallMs 表示求解阶段耗时，wallMs 包含批次记录的准备和评测；首次原目标验收时点另按检查/评测事件确定。未解决运行不把停止时间当成成功时间，历史归档回执不冒充当前新验收。

完成条件：每项比较能对应明确假设、固定配置、完整分母及数据来源；改进若只增加活动量，没有更好的原目标结果或有效成果消费，则保留默认策略或缩小适用范围。零通过或用量缺失时，不宣布效率提升。

参考：[比较实现与报告口径](../scripts/mathematics/compareMathRuns.ts)、[三组比较](../examples/imo2026/COMPARISON.md)、[模块实验](../examples/components/EXPERIMENTS.md)、[PutnamBench 样本与限制](../examples/putnambench/README.md)。

**实施顺序与暂缓项**

推荐顺序：阶段一诊断 → 阶段二逐项改进 → 离线回归 → 后续真实对照；阶段三按 Lead 故障损失证据单独排期，规模实验在四人配置的流程和预算校准后展开。

运行时行为变更同步对应模块与方法身份，使用新构建、新计划；既有运行保持冻结语义，不静默迁移或重启。每项代码变更运行受影响的本地回归；涉及运行时边界时完成 typecheck 与 headless bundle build。

本轮暂缓：提高八人上限、无限增殖 worker、自动选举数学领袖、全员广播共享板、任意 peer 改任务图，以及将 advisory 失败升级为全局数学否定。有限轮次或时间下启用 capacity exploration/refill 是另一项策略实验，现有要求轮次和时间均无限的自动触发条件先保留。

最终交付以实际成果说明吸收程度：哪些等待减少、哪些结果更快被使用、哪些原目标通过；没有实测收益的改动继续标为流程能力。
