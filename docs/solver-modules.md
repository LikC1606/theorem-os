# 解题模块与交接协议

M1–M5 表示运行时的决策边界，不是五个依次执行的解题步骤，也不等于五个 agent。研究检索、路线规划、引理证明、原题集成和独立验收都会使用其中多个模块。增加角色数量不能替代明确的数学产物和消费关系。

## 模块边界

| 模块 | 唯一职责 | 输入 | 产物 | 不得冒充的完成状态 |
| --- | --- | --- | --- | --- |
| M1 执行 | 在指定隔离工作区执行一次模型工作 | M4 上下文、操作类型、worker 与会话 | 候选源码、研究笔记、会话状态及来源信息 | 模型返回 `completed` 不代表 Lean 通过或原题解决 |
| M2 证据 | 对固定版本、精确目标执行独立检查 | 问题身份、commit、源码、任务类型、条件及环境 | 绑定源码与声明身份的 `ProofCheck` / `TaskProof` 和 Lean 回执 | 引理通过、条件证明通过不代表原题通过；旧 JSON 回执不能直接授权恢复后的验收 |
| M3 搜索调度 | 选择数学上可推进且能分配的工作，决定操作和可恢复重试 | 任务图、依赖、路线、预算、存活 worker 与 M5 分配条件 | 排序后的候选任务、操作或停止原因 | `ready`、有新计划、存在存活进程不代表有证明进展 |
| M4 上下文 | 为当前工作组装精确且版本一致的输入 | 原题、冻结上下文、assignment、依赖接口、回执与相关交付 | 上下文及包含/省略清单 | 检索命中、笔记摘要、历史通过记录不代表当前输入已获证明 |
| M5 职责分配 | 将工作分配给允许承担它的角色和工作槽 | M3 候选任务、存活角色、owner/engineer 约束 | 指定 worker 的任务或审阅职责 | 分配成功、Reviewer 同意不替代 M2 或 S3 |

实现入口在 `src/solver/modules/`：`execution.ts`、`evidence.ts`、`search.ts`、`context.ts`、`organization.ts`。`index.ts` 绑定模块版本；行为变化需要同步运行身份，不能让旧任务静默换用新语义。

运行控制与证据服务的实现边界如下；这些文件承接模块结果，不以模型自述替代严格证据。

| 实现入口 | 职责 |
| --- | --- |
| `src/solver/research.ts` | 编排会话启动、执行、恢复和交付；串行化整题检查入口 |
| `src/solver/workerProofLifecycle.ts` | 统一证明就绪后的 writer 停止确认、源码冻结与固定快照检查 |
| `src/solver/researchUsage.ts` | 管理当前模型轮次和会话的用量事件、请求准入与收据结算 |
| `src/solver/usageBudget.ts` | 计算累计用量与共享预算状态，不执行模型或证明检查 |
| `src/solver/cooperation.ts` | 管理任务、交付、集成与通知；分别处理 Lead、peer 派发，共用等待和前沿恢复逻辑 |
| `src/math/verifier.ts` | 核对固定源码与目标身份，执行 Lean 检查和官方验收，生成回执 |
| `src/math/verifierCheckout.ts` | 负责验证工作树的创建与回收；失败、异常和取消均进入同一清理路径 |

S1 归档由 `archive.ts` 管理，S3 最终验收由 `evaluation.ts` 管理；S2 学习仍是未来扩展。

## 数学工作阶段

研究检索应交付可核对的线索、阻碍或明确的引理提案。路线规划应把线索变成可执行任务，并说明谁会使用结果。引理证明必须有固定 Lean 类型和独立回执。原题集成应展示已检查引理在原始目标上的实际应用，重新检查合并后的源码。独立验收检查完整原题及适用的官方比较器。

这些阶段可以交错进行。研究完成只表示调查已经交付；引理检查通过只表示该声明成立；只有完整原题通过 S3，才能报告最终验收通过。官方结果还要区分 `official: true` 与普通宿主 Lean 检查，不能由内部通过数推断上榜或官方提交状态。

## 数学路线与研究结论

Lead 先根据原题、定义和已有发现判断可行的数学路线，再提交任务图。它应在 `RESEARCH.md` 的单个 `math-plan` JSON 围栏前保存简短的路线论证，把新任务的关键推断和消费者写入 objective；尚不清楚的推断交给研究任务调查。直接证明更合适时可以直接安排原题，不强求拆成更多引理。规划期间继续保持 Lean 源码只读，诊断和证明交给对应 worker。

研究与证明 worker 应保留可供他人继续使用的数学论证、精确假设和剩余缺口，区分数学推断不足与 Lean 名称、类型、策略问题。宿主在原有笔记读取上限内保存完整研究 finding，不再先截到 5000 字节；交付的 `findingDigest` 由宿主绑定完整产物，短摘要与完整 JSON 或 Markdown 结果可以可靠关联。M4 不再固定截取交付摘要的前 1000 字节；相关的完整研究 finding 与重复交付元数据分开选择，正文优先，带任务版本及可用的固定笔记引用。预算不足时整条省略并记录在 manifest，完整类型与前提仍是必需输入。研究发现和路线说明继续只作为 advisory，不改变 M2 或 S3。

辅助任务的必需上下文现在包含消费者的完整数学接口、假设、任务版本及普通依赖或备选路线的使用关系。M5 从完整任务图单独投影同组或公开消费者，因此跨组尚未完成的公开目标也能说明辅助引理的用途。投影同时绑定当前任务 ID 和数学版本，空投影也不能跨任务或跨版本复用。该投影不递归导入消费者的其他前提，不携带证明或验收结果，不加入执行依赖闭包；跨组私有消费者保持不可见。工作契约与原题焦点使用同一消费者列表，避免只显示 ID 却丢失精确命题。

当前派发的失败反馈与当前原题宿主反馈属于必需输入，不能被可选预算省略或只留下错误前缀。会话重建的 `RESEARCH.md` checkpoint 按实际预算完整选择，不再固定截断到 5000 字节；预算不足时整段省略，并必需保留工作区根路径、完整字节数、UTF-8 SHA-256 和回读指示。其他任务的错误及完整 checkpoint 正文仍参与可选预算，必需内容超出硬限制会明确报错。会话职责隔离和轮换规则保持原语义。

这项提示调整参考 [OpenAI Docs 的推理模型提示建议](https://developers.openai.com/api/docs/guides/reasoning-best-practices)：明确数学目标与成功条件，提供可用上下文，避免要求输出内部思考过程。源码核查表明当前默认模型已经是 `gpt-6.1-sol`、`xhigh`，本轮不更换模型、不调整预算。以上仅验证输入和流程限制得到修复，尚无真实解题成功率证据。

`refuted` 或 `needsDecision: true` 的研究交付另形成必需的 research challenge，避免反向可行性审阅只留在可选摘要里。宿主要求 finding 摘要、交付和任务版本一致，绑定固定笔记 commit、依赖与相关 OR 路线拓扑；缺少绑定的旧记录保留为普通研究材料。Lead 对本轮展示项显式选择 `revised`、附证据引用的 `disputed`，或带具体 `waitsOn` / `reopenOn` 的 `deferred`。每批最多 8 项、约 32 KiB，未展示及晚到项继续排队，并尊重私有范围。

延后项等待精确版本的证明输入；本进程重新核验其无条件通过后再次进入决策，恢复出的 JSON 不授予这种信任。计划不能通过删除来源或等待目标静默清除待办，数学合同或路线变更则使旧决定失效。反驳本身仍是 advisory，不自动判原定理为假、停放任务或改变验收。

## 早期路线检验

不确定的分解应先明确最难的构造或估计，并分别检查两个问题：所提引理是否足以推出消费者，以及这些引理本身是否可行。Lead 使用既有任务字段安排检查；普通直接证明不要求增加调查。

- 普通依赖图中的消费者可用 `conditional:true`，在固定类型的引理尚未证明时先检验连接。带 `proofRoutes` 的原目标仍等待已检查路线，提前验证应放在该路线的 closing lemma 上。
- 独立质疑使用不带证明类型的 `research/sketch` 与 `reviewScope:"feasibility"`，`dependsOn` 引用需要检查的消费者和核心任务。这些是调查输入，不要求先完成证明；消费者不得反向依赖该调查而形成环。
- 四种任务排序策略优先提供一次尚未尝试的可行性检查，其次是尚未尝试、具有真实消费者的条件连接。已有路线检查运行时不额外提升其他检查，尝试后恢复原策略排序；暂停、预算、归属及路线就绪条件继续生效。
- M5 根据完整任务图排除被审任务已记录的作者、显式 owner 及原目标指定的 engineer。输入归属变化后撤销不再独立的派发，保留已有草稿与显式 owner，并将迟到交付标记为过期。检查使用 reviewer 职责，在进入、切换被审任务、重新派发或返回证明时隔离会话；同一派发的连续检查点仍可恢复。没有独立可用 worker 时保留调查待办，其他可执行证明继续推进。

可行性产物使用既有的 `supporting/refuted/inconclusive` 研究结论，重点保留核心缺口、量词和统一常数、数量级、边界情形及可复现的判别证据。它不会生成证明接受，也不会把条件桥梁变成完整原题证明。宿主不自动判断数学路线是否减难；规划者仍需明确被审推断及其消费者。

对于明确依赖 typed lemma 的消费者，宿主可提前派发一次连接检查，检验这些输入是否足以证明消费者。`assignment.connectionCheck` 固定消费者、输入版本、派发 seed、问题和环境身份及相关路线摘要，不改 `taskVersion` 或原题。显式 `conditional:false` 禁用这类提前派发；未完成的非 typed 输入、私有输入和暂停控制仍保留原门限。辅助引理仅在存在未完成、未停放且组仍可执行的正式消费者时自动获得提前连接检查。OR 原目标继续等待已检查路线，提前检查放在 closing lemma 上。首次优先级按当前派发及证明版本判断，不受旧合同累计 attempts 干扰；独立且有用的工作仍可执行。

条件检查保守保留派发时仍未证明的 typed 输入，即使正文可能未使用其中某项，也要等这些条件关闭后再做严格无条件集成检查。只有无条件复验得到的新鲜实际引用才可缩小后续依赖；不能根据正文字符串或条件回执推断前提已经证明。已无条件集成的消费者继续按实际引用保留，未使用的旧计划输入改变不会自动使其失效。worker 收尾提交若仅改变 `RESEARCH.md`，且本进程核验的实际引用、canonical 源与环境仍有效，可保留原证明及回执；任一其他 tracked 路径改变仍走严格检查。

连接产物复用现有条件证明回执。宿主仅在临时投影里提供固定输入，不要求 worker 添加占位证明或新假设；输入全部获证后，再检查合并后的无条件消费者。恢复后的 JSON 不直接获得信任，必须重验；输入合同或相关路线改变使旧许可失效。条件连接成功不代表输入成立，也不等于原题验收。

有限 Boolean 推断可先用 `theorem-os check-finite --input FILE` 或 `--json JSON` 复算。输入是 `theorem-os.finite-boolean-cnf.v1` 的变量、固定赋值和 CNF 子句；输出绑定规范数据与原始输入摘要，保留完整赋值计数、满足数及有界 witness。超过公开枚举规模限制时返回 unsupported，不能报告矛盾；没有新增墙钟截止。结果仅针对输入约束，仍是 advisory，须连同精确数据进入研究证据，不能代替 Lean 或 S3。`examples/finite/old-b1-nine-constraints.json` 重放旧九行约束，在 256 种赋值中得到 5 个满足染色；它只否定该组约束的旧矛盾推断，不否定几何构型或原题。

本轮仅验证调度、作者隔离、上下文和会话恢复行为，尚无实题成功率收益证据。停止的求解任务没有部署或重启。

## 减少无效消耗

本轮按调度、重复识别、并行路线的顺序改动流程，没有增加固定时限或固定回合截止，也不自动取消备用调查。

1. **排序落实到实际分配。** 默认 M5 让 researcher 和 engineer 按 M3 的同一顺序选任务，仍遵守显式 owner、指定 engineer、恢复派发与审阅独立性。已就绪原题优先；其次推进有活跃消费者、可立即使用已检查输入的引理。暂停或停止的消费者、停用或预算耗尽的组不能抬高辅助任务优先级；独立探索继续保留，但不挤掉已就绪的原题消费。
2. **以局部输入和候选识别重复。** checkpoint 的局部输入只跟踪当前数学任务、依赖及真实关联交付，无关 canonical helper 或同组普通笔记不会重开任务。保留原始摘要用于恢复，另外计算排除摘要改写、代码块偏移等表面差异的候选摘要；普通论证或未完成 JSON 标为未分类草稿，继续保留。候选未变化只给提示，不设新的停止阈值。完全相同的失败源码仍走原精确缓存；移动或改名后的相同目标只生成关联尝试提示，不复用验收。不存在或有歧义的声明不生成这种目标指纹。已记录障碍可通过可选 `blockerId` 续接，避免仅因改写描述而丢失历史；数学合同、环境或依赖证据变化仍独立处理。
3. **并行围绕具体问题，路线按证据投入。** 普通 worker 上下文展示可见的并行问题及其任务版本，要求区分核心证明、反例或可行性、精确库连接和消费者应用；没有独立问题时允许等待。独立可行性审阅不接收这些协作输入。OR 路线按局部阻塞、closing 的当前检查结果、已检查输入与当前占用排序，保留全部前沿并单列首选路线；运行中的派发不改变输入，未就绪的待恢复草稿可重新比较路线。前提数量不作为数学难度或证明用时估计。

这些记录用于定位浪费来源，尚不能给出真实节省比例或难题成功率收益。原题冻结、固定源码检查、恢复复检与独立 S3 验收继续生效。

## 提案如何进入证明

开发代码已接入以下协议，尚未部署到停止的求解任务。工作契约入口为 `src/solver/modules/contracts.ts`，研究提案记录入口为 `src/solver/researchHandoffs.ts`。

```text
研究/检索结果（advisory）
  -> lemmaRequests（精确目标、完整类型；建议说明原题用途）
  -> pending 提案进入 Lead 的必需上下文
  -> 接收者采纳 / 拒绝 / 延后，并保留决定
  -> 采纳后生成 typed task；规划者应连接原题 consumer
  -> M3 检查可执行性，M5 分配，M4 编译输入，M1 证明
  -> M2 检查固定声明，检查合并后的版本
  -> 原题 consumer 使用已检查结果，填补实际缺口
  -> 完整原题检查与独立审阅 -> S3 最终验收
```

工作契约统一记录当前阶段、责任、输入、产物、消费者和验收方式。Lead 规划原则上只改计划；兼容的源码修复仍走宿主检查和集成声明复检。提案记录使用 `pending`、`adopted`、`rejected`、`deferred`；这些是提案处理状态，不是证明状态。

`assemble` 是宿主对固定候选执行整题检查的阶段，不派发模型、不消耗模型轮次，也不授权 Lead 再编辑证明。其工作契约由宿主负责，产物为固定原题检查，之后进入独立审阅与 S3。

盲译与陈述审阅继续使用独立的固定快照协议。盲译只接收形式陈述和定义，不接收研究提案、任务图或预期数学解释；之后的比较阶段再接收预期含义。两者的结论也不授予证明通过。

同一次声明准备或审阅同步共用固定 commit 的源码读取、注释遮蔽和声明扫描；同步的两轮快照共用这份准备，每个目标仍独立生成定义视图、字节上限、摘要和完整依赖审计记录。共享数据不跨调用保存，返回对象互相隔离，原题只保留自身声明头，helper 视图移除所有 theorem/lemma。

helper 类型在独立 section 内作为单个 Lean term 解析，不直接拼接为可执行命令。已有 helper 恢复自身声明的 namespace/section/open；待建 helper 只复用同文件、同命名空间且查找上下文一致的原题声明，否则仅恢复所请求的命名空间。多个原题上下文冲突时保留诊断并报告不可确定，各 helper 的 open 不向后续目标泄漏。原题仍读取固定声明，local variables、notation、universe 和 instance 等其他局部状态不保证恢复，所有投影结果仍是 advisory。

合作模式由 Lead 在 `math-plan.tasks` 中提交完整任务图，以匹配同一精确目标与类型的任务识别采纳；匹配还保留路线、条件、前提和原有依赖要求。

规划者应把采纳结果接到明确的原题消费者；当前宿主不强制存在这条连接，仅有一个同类型任务仍不能证明它会推进原题。响应可带以下拒绝或延后字段；本例只展示决策字段，Lead 仍须提交完整任务图：

```json
{
  "handoffDecisions": [
    { "id": "HANDOFF_ID", "status": "rejected", "reason": "具体原因" },
    { "id": "ANOTHER_HANDOFF_ID", "status": "deferred", "reason": "等待精确估计通过", "waitsOn": ["estimate_lemma"] }
  ]
}
```

`waitsOn` 必须是本次拟提交计划中非空、去重的形式证明任务 ID；宿主保存其精确数学版本。只有全部等待目标完成合并、通过无条件检查且具有本进程认可的验收记录，提案才重新变为 `pending`。无关进展、条件证明、目标改版及 JSON 中的历史通过标记都不能触发；恢复后先按原协议重新核验。重新进入决策时保留先前决定，并标记 `reopened: checked-prerequisites`，仍需接收者重新采纳、拒绝或延后。全部已经通过的目标不能再次用作延后理由。

派发记录冻结本轮需要处理的 `handoffIds` 和对应 `handoffActivations`；提案重新进入决策或决定发生变化后，旧派发不能处理新一轮提案。默认每批最多 8 项，完整提案 JSON 的 UTF-8 大小最多 32 KiB；交付按到达顺序处理，同一交付内优先展示依赖提案，长依赖链可分批推进。若首项本身超过软预算，单独展示并继续受必需上下文硬限制检查，不截断类型、前提或依赖。

相同来源任务版本、精确提案及版本化输入的重复交付合并为一项待办，保留全部来源和旧交接 ID；新增重复来源不会重置决定或唤醒周期。所有新决定绑定 `contextDigest`，依赖数学版本改变后重新核对。宿主与恢复派发都接受保留的旧 ID，并执行相同的过期检查。模型上下文保留完整数学提案，重复来源以固定大小的 `sourceSet` 数量、摘要及 `COOPERATION.json` 引用表示，读取时核对交接身份、输入摘要和来源集合摘要；批次按这一投影计算大小。

本批完整提案进入必需上下文，不占用可选提示预算。剩余队列显示数量和来源，连同晚到项在后续决策中处理；即使普通计划输入摘要相同，也不能漏掉剩余批次。相同无效响应的停止重试规则继续生效，恢复时也不能重新采纳会丢失队列来源的被拒计划。正常完成的响应漏掉已展示提案会被拒绝。

模型规划不得隐式删除或改写未处理及仍在等待的提案来源、已有前提和路线数学版本；宿主在修改图前检查，显式人工编辑仍按原协议使受影响交付失效。后续 consumer 可以继续引用先前批次的任务。其他排队提案依赖一个提案时，采纳它必须保留原任务 ID，宿主不自动改写依赖。

等待期间可按提案 ID 显式修改等待合同、拒绝或取消自动唤醒；修改等待合同仍须保留提案来源和原始依赖。省略 `waitsOn` 的延后决定兼容旧记录，不自动唤醒，也不继续锁定等待来源。采纳提案不表示引理通过，更不能把研究者的结论当成原题前提。

## 恢复与保存产物

`continuation.adoptedResearch` 把有效的研究采纳决定连接到当前版本的引理，分别列出计划消费者、通往原题的路径，以及 Lean 回执中的证明、声明和条件性消费者。尚未证明或尚无消费者的采纳项仍显示，供 Lead 判断后续应用；不强迫每个探索提案立即绑定原题消费者。缺失或过期引用的覆盖状态为 `unknown`，不能从空数组推断成果无用。模型上下文、各自范围内的 `COOPERATION.json` 和 `inspect` 共用这份映射，私有路线结果不跨范围泄露，采纳不改变调度或证明验收。

同步计划到 `RESEARCH.md` 必须逐字保留数学文本，包括 LaTeX `$$` 和 JavaScript 替换字符串中的特殊序列；同步本身不能修改任务合同或使已完成调查失效。尚无任务的初始规划也可从保存的完整合法计划恢复，仍检查原题覆盖、排队来源、任务身份与前沿恢复约束。

Lead 每次派发的源码基线保存为 `leadSeedCommit` 并 pin。恢复先保存并 pin 当前草稿，再把相对基线的声明变更及合法新增 imports 合并到当前 canonical，随后独立复检已有证明。是否已提交不能决定是否丢弃草稿，也不能把旧工作区整树替换为 canonical。冲突或旧快照缺少可信基线时，保留带固定 commit 的 advisory 草稿交付供 Lead 回读，canonical 保留已合入证明；草稿本身不获得证明接受。

模型请求失败后，已保存、通过合同检查且实际改变任务图或交接决定的普通 Lead 计划可继续消费，不重复初始规划。空响应、无效计划、未改变的旧计划、失效派发和不满足前沿恢复条件的产物不能凭请求失败获得接受。

研究与 sketch 的未完成产物按任务版本、worker 和派发基线保存为 `researchDrafts`，保留固定 commit 与产物清单并 pin；停滞计数仍由独立的 `researchCheckpoints` 管理。切换职责再返回时，只恢复匹配该派发的笔记和草稿。canonical 已推进时，以当前源码重新建立基线，旧源码草稿作为 advisory 保存，不能覆盖其他成员已合入的证明。旧状态缺少可信快照时，清除其他题目的继承笔记并重新准备输入，不能把这些笔记当作当前题目的新发现。

研究请求失败也保存草稿，再按原规则重试；失败本身不增加数学停滞计数，不完成调查，不采纳引理提案，也不解锁消费者。关闭失败会话可能等待其他操作，宿主在关闭完成后再次确认任务归属；期间被修订、删除或暂停的任务，其旧失败不得覆盖新任务状态。晚到的旧审阅失败或结果也不能改写已取消、替换或完成的审阅。

会话启动前、启动重试前及启动完成后都核对派发归属。启动或退避期间任务被撤销时，退还尚未使用的回合、关闭旧会话并继续选择当前任务；路线回合在等待期间耗尽时同样释放预留，让 worker 可以执行其他路线。Lead 在共享回合只有预留、尚可能退款时等待结算，不把预留误当作耗尽而提前退出。已实际开始的请求仍计入回合，不因过期而退款。反向翻译及陈述审阅关闭失败会话后也重新核对归属，取消后的旧失败不进入请求重试。

最终审阅、反向翻译及陈述审阅每次派发都生成持久 `assignmentId`，即使 commit、worker 和 workspace 相同，旧结果、拒绝、中断、release 和启动回调也不能操作新派发。完成或失败后释放 reviewer 归属，取消回调不重开已结束审阅。旧状态和旧 action 都没有派发编号时保持兼容，首次重新派发后必须匹配新编号。

## 增量交付与条件证明

初始任务图为空时，Lead 可向提示词指定、绑定本次 nonce 的 `DELIVERIES-<digest>.jsonl` 追加完整的 `{"kind":"plan","baseVersion":"当前基版本","summary":"路线说明","tasks":[...]}` 行，提前发布一次可执行计划并继续自己的会话。宿主冻结事件、按普通计划合同检查并保存 receipt；半行等待补全，旧 nonce 或旧基版本不能发布。只有这次自发布允许 Lead 沿用当前派发，人工改图仍使旧派发失效。peers 从 canonical 源码开始，不继承 Lead 未交付的证明草稿；恢复和最终笔记交付保留已接受图，显式新计划及源码仍走正常检查。该机制没有增加规划时限或要求提前交付不成熟类型。

增量日志中的显式交付编号只在同一 worker 的同一派发内去重。宿主为全新派发生成持久化的 `assignmentId`，结合任务 ID、数学版本和源码基线生成 `assignmentKey`；恢复原派发保留身份，重新分配后可以复用交付编号。同分工重放仍保持幂等，省略可选摘要也能正常保存交付记录。异步证明检查结束后，仍须核对当前派发和真实依赖版本，过期结果不能更新新任务。

证明就绪后的冻结与恢复统一由 `WorkerProofLifecycle` 处理。新快照必须先取得 writer 已停止的确认，关闭会话后再次核对分工与源码约束，再提交固定源码并检查。停止未确认时先持久化 `writerStopUnconfirmed`，即使普通关闭随后失败，恢复也会拒绝在该工作区重新打开 writer；已冻结的快照可直接继续独立检查。

worker 交付日志按行持久保存游标；停止、验证器不可用或宿主异常保留当前行，恢复后继续消费，已经成功的前缀不重放。坏 JSON、非对象输入、格式错误、确定不存在或不继承原题基线的 commit 及明确的源码约束错误只拒绝一次。超长行以至多 64 KB 的缓冲读取并丢弃，丢弃状态跨轮次及恢复保存；遇到换行后继续消费，不能把尾片当新交付，也不阻塞另一个兼容日志。人工 edits 继续使用原有严格读取规则。

人工编辑在获得串行写入权后重新核对 `baseVersion`，排队的旧计划不能覆盖较新计划。纯合同校验通过后，任务图、`planVersion`、`applied` 和待同步标记一起保存并前移游标；慢语句准备与证明复检在锁外执行。持久 `pendingValidation` 隔离受影响子图及消费者，无关任务和后续暂停操作继续推进。固定快照核对 canonical、问题、环境、任务、依赖及证明身份后才发布，过期成功和失败均不能覆盖新状态；canonical 推进则重新准备。后台同步失败保留 `pendingSync`，恢复补齐而不重放计划，停止时收齐全部后台工作。确定的 JSON、计划合同或版本冲突才永久拒绝。成功前缀按字节游标保存，包括空行、多字节文本与 CRLF。

计划快照在复检期间失效时，等待在途检查与清理完成后停止后续检查，跳过旧快照的声明准备；排队等待声明准备的工作在出队时也重新核对当前性。提前结束的整批结果不发布，所有待验证目标由新快照接续，canonical、环境或问题身份改变仍走原有 rebase 流程。验证器不可用、身份、I/O 和清理错误继续传播，确定的旧数学结果不写入新状态。

证明合并区分确定的交付拒绝和宿主故障。停止、I/O 错误及验证器不可用保留已通过的交付和原 canonical；确定的证明、依赖、源码冲突或回执身份不匹配仍明确拒绝。canonical 已接受后的语句准备失败保留 `integrated`；重放补齐审阅同步和交付记录。同一进程内重试复用已核验的固定 proof，但合并版本仍需独立检查；JSON 恢复后原有重新核验要求不变。已记录交付的去重不会跳过尚未成功合并的条件父证明，同一固定证明的增量交付和回合结束交付也不会重复记账。worker 退出时仍为 `running` 的任务回到 `pending` 并保留派发，错误继续记录在 worker 与任务反馈中；已经确认的交付失败不受该清理影响。

初始证明检查可并行，同一派发与 commit 的在途交付只检查一次。canonical 集成使用独立串行队列：短锁冻结任务、派发、依赖和 canonical，锁外合并并严格检查，再用短锁核对并发布。慢合并检查不会占用人工控制操作的全局队列。期间任务被暂停、撤销或数学合同改变时，旧成功和失败都不写入新状态；canonical、依赖证据或仍活动组的配置推进时重新合并复检，不消耗模型回合。组预算调整不能把仍在等待集成的已检查交付记成证明失败。

批量复检和快照恢复按精确目标归属证据；核对批次、目标顺序、声明 hash、session、check、receipt 和汇总状态后，保留独立通过或确定失败的结果，只为无法归属的目标补单项检查。混合基础设施故障、清理失败和中断不能拆成可消费的数学证据，恢复报告也不能将其中的单条成功回执标为新鲜证明；成功输出中的 `timeout` 等名称本身不表示中断。

已接受的 helper 或原题陈述审阅，仅在精确形式快照、环境、数学意图和前提均未变化时跨描述版本复用，更新当前任务及依赖版本，并使旧版本交付失效。完整类型、引用依赖、意图或假设改变仍要求重新审阅，未完成审阅不复用。

依赖的说明或规划版本变化不改变已审数学接口的语义身份；快照仍保存完整依赖摘要供溯源，冻结审阅文件不能改写。原题及固定候选实际引用的 helper 才是最终候选的必要陈述审阅。缩减范围必须来自本进程新检查的整题回执与所有原目标的完整 Lean 引用报告；缺覆盖或 JSON 恢复保守要求全部配置审阅。必要审阅可跨证明任务暂停、停止或路线耗尽派发，仍受模型预算与固定快照身份检查约束。候选待审期间 Lead 等待审阅完成。

上下文溢出单独恢复：先完成普通源码与笔记保存，关闭旧会话，清除可选提示预算后重新编译完整数学输入。失败的新会话输入按任务、源码、环境、模型和预算身份持久去重，恢复不能重置拦截；相同输入无法容纳时明确报告容量阻塞，不引入解题时限。鉴权及宿主完整性故障不因此重试。

标准 M2 的精确投影检查使用单次运行内的有界缓存和同信号并发合并，按完整 Git 投影树、问题与项目、目标顺序及声明 hash、合同、依赖、保留目标、条件、原调用预算、密封环境和实际工具身份复用验证器产物。每次仍重新检查源码权限，重算相对当前 seed 的声明和 import 改动及实际引用；源码或 seed commit 自身不同不阻止等内容复用。无法确认工具身份或存在可变库路径时绕过缓存，等待后工具或环境漂移走基础设施恢复；`Infinity` 保持不变。

复用保留原回执的 target commit、session 和时间，另用 `projectionReuse` 关联当前投影与原检查投影。宿主在写入自身注解前核验进程内信任、两个完整 tree、当前源码投影、授权差异及原收据，并 pin 两个投影。复制、修改或恢复的 JSON 不恢复信任。缓存只保留通过及可归属的确定 Lean 失败，瞬态故障不缓存，S3 仍独立检查。

公共集成入口可将当前已就绪、同组、互不依赖且声明改动不重叠的已检查 lemma 合批，最多 32 个，不等待凑批。合并到同一个 disposable union 后，每个目标必须要求相同的完整投影；逐目标经过宿主身份检查，全部通过且任务图、路线、组控制、依赖及 canonical 仍匹配才一起发布。混合确定失败、投影差异或合并冲突回退单项新检查，不能把大投影的收据用于缩小后的树。同一失败组合在当前进程中有界去重；中断、清理、基础设施及收据身份故障直接传播，不展开成多次逐题重试。已接受成员继续通过现有交付补发路径完成发布。

兼容的全局 `DELIVERIES.jsonl` 仅带任务及版本，无法区分同一版本下旧派发迟到的新行。新交付使用宿主为当前 assignment 指定的独立日志文件；旧日志的保留不代表它具有完整派发隔离。

父证明的条件检查把未完成子引理作为显式假设，投影与集成补丁都按文件及完整声明身份匹配，保留不同命名空间或文件中使用的 helper，集成补丁排除假设子声明的草稿。投影中的词法引用筛选仅用于清理失效 wrapper，不建立证明依赖证据；有歧义时保留声明交给 M2 检查。子引理通过后，宿主复用父证明，重新检查合并版本；条件检查的回执不能代替这次无条件检查。

## 原题前沿

进度报告、M3 排序、上下文和恢复共用已记录任务的闭合判断。`completed` 研究任务只结束调查；如果其数学前提尚未证明，原题前沿继续指向这些前提，多层研究交接和 JSON 恢复都不能把它们隐藏。缺失依赖或依赖环保持未闭合。

已独立检查的无条件形式接口可封装旧的内部规划依赖；不能因此重开已经实际证明替代的私有前提。报告仍展示被暂停的数学分支，调度继续排除已暂停路线。该判断只描述记录，不代替恢复后的独立复检或 S3。

恢复沿用 M3 的路线遍历，逐原题保留所有有效 OR 分支上的失败前提。已停放且看似就绪的分支不能遮住另一活动分支的真实缺口，显式暂停、停止或预算耗尽的任务及组不进入恢复候选。停放的证明义务仍可作为 Lead 诊断缺口，用于换路线或引入新数学输入；这不解除停放，也不授权重试原证明。

局部任务的必需路线提示保留指定路线及最多四条相关或优先路线，完整安全索引写入 `COOPERATION.json.routePriority.routes`，完整前沿写入 `frontierFocus.taskIds`；上下文携带数量、摘要和真实字段引用。精确任务与消费者接口继续是必需输入。大量省略项的 inline manifest 只展示有界预览和完整清单引用，`CONTEXT-MANIFEST.json` 仍保留全部省略记录，避免单是元数据就撑满局部上下文。

运行时分别判断“还有任务可做”和“原题相关工作能否推进”。原题证明路径、指向当前卡点的定向研究及其前提属于原题支持工作；没有消费者连接的辅助链不计入。已完成的调查仍须检查其数学前提，不能仅凭 `completed` 宣称原题可以推进。根候选可按原题范围筛选，但检查依赖时保留完整任务图及角色、归属、路线约束。

已经实际失败的原题前沿缺少可派发、可继续或正在运行的支持工作时，Lead 可以在独立探索仍可运行或正在运行时发起定向恢复。恢复规划不占证明槽，独立工作填满同组并发容量也不阻止规划；任务及组的启用、回合预算和路线阻塞约束仍然生效。恢复沿用精确数学输入去重；相同输入已评估后，无关进展不会重复创建恢复请求。已有的条件连接验证、证明集成和陈述审阅继续按原规则执行；从未尝试的导入任务仍走原来的首次恢复流程。连续研究模式可在已有恢复结论上补充定向调查，独立探索不被自动取消。

研究或进度成果可用 `mathematicalGap` 持续记录原题的数学缺口：精确 consumer、上一缺口、实际减少的部分、仍缺的量词和强度、证据范围及重试条件，后续报告可引用 previousDeliveryId。宿主绑定问题、环境、来源、消费者和传递依赖版本；输入变化后保留旧证据为历史，不能把弱结果或条件充分性当成核心前提已证。组私有范围同时约束历史与当前来源/消费者。必需上下文最多展示八项、每项 8 KiB、合计 32 KiB，省略内容有摘要、数量和 `COOPERATION.json.mathematicalGaps` 完整读取句柄。

## 当前任务的知识复用

附带知识库的新运行由 M4 自动检索当前任务可参考的历史定理，不再只依靠 agent 自行发起查询。引理使用完整闭类型，原题使用冻结陈述及绑定参数，研究任务使用调查目标；Lead 优先查询原题尚缺的前沿任务。目录元数据来自运行开始时已核验并绑定摘要的快照，构造候选不加载归档源码对象。

Lead 的三个自动检索目标先覆盖当前证据排序的首选路线，剩余名额按原顺序保留其他活跃前沿；已停放的分支不进入该前沿。检索和残余诊断消费者共用相同的目标选择及当前环境身份，避免检索名额被旧阻塞路线占满，或把其他环境的历史检查当作当前缺口已经闭合。此排序只影响 advisory 检索，不改变路线、任务状态、检查收据或验收权限。

当前 worker 已有完整且输入匹配的 Lean JSON 目标时，M4 优先使用其局部假设和残余目标检索。读取前重新核对完整本地导入闭包、项目配置、固定依赖环境、实际编译工具及原始输出摘要；只有正常退出、完整捕获且能精确对应当前任务版本与唯一完整声明的目标才可使用。每条诊断不超过 16000 字节，读取器最多保留八条匹配消息并记录其余数量；独立 residual 和 case 分别查询，受支持的局部声明仅为检索构造成闭合视图，复杂语法明确回退。稳定排序后按消费者轮转分配最多八个请求，观测保留逐项检索、省略、返回候选及来源身份；陈旧、截断、中断、歧义或超长材料回退到原有完整接口。

每次最多查询三个目标，各保留最多三个候选，每个目标提示最多 4 KiB。超限时丢弃完整候选并记录数量，查询自身超长则明确标为未检索。候选经过普通可选上下文预算筛选，省略记录进入 manifest，当前任务的完整类型与原题前提仍为必需输入。这些限制不改变解题时长或回合数。

同一次上下文构建的定理检索共用目录分词、声明分组和词频准备，路线记忆检索也仅准备一次陈述与摘要词袋。两类检索共用合法目标顺序，各目标仍使用各自完整查询、局部假设及目标形状独立评分，结果与逐项检索相同；重复请求的返回对象也不共享可变数组。共享数据只保留在本次调用内，后续调用重新读取元数据；空白或超长目标保留各自未检索记录，不挤占其他目标的结果位置。

提示绑定当前 consumer、检索输入和目录摘要，展示历史类型预览、依赖覆盖及环境匹配；复用前仍要读取完整类型、全部前提与源码上下文。候选不进入固定证明审阅、盲译或陈述比较，不提供历史证明正文或回执，不增加任务的通过数。实际应用仍走 M2 与 S3。

知识库必须由 `run --knowledge-base FILE` 显式绑定。`inspect` 区分未启用、旧记录覆盖未知、已检索及被上下文预算省略；检索观测保留 128 条和丢弃数量，完整事件仍保存。模型可在同一成果 JSON 中填写 `knowledgeUses:[{id,catalogDigest,declaration:{name,file}}]`；合法引用先记为 `reported-attempt`，只有固定检查的当前消费者证明实际引用精确声明和文件才记为 `checked-reference`。历史来源始终是 `model-reported-origin`，伪造或错误元数据只被丢弃，不影响证明检查。

使用记录可附 `application:{expression,expectedType,context:{file,declaration},arguments?,additionalPremises?,typeclassIssues?,adaptationSteps?,remainingGoals?,reconsiderWhen?}`。宿主只对模型选择的应用做检查，每次发布最多四项新检查；记录 elaborated/failed/unavailable、实际引用、原始产物和完整输入身份。证明擦除副本中的局部声明可作为假设，应用展开不证明这些前提、不代替 M2 或原题闭合。精确匹配的目录、任务、提交源码、导入/配置闭包、环境、工具和产物才能复用旧检查；输入变化重新检查。M4 最多回忆四项同目录经验，超长内容保留完整本地 JSON 读取句柄。等待检查期间再次核对任务、派发、证明和环境状态，过期结果不发布。

`compare` 和 `sample-putnam` 的 prepare 阶段可显式绑定知识目录，将只读快照、digest、格式和 transfer/recovery 模式冻结到计划及每个 launch。默认 transfer 拒绝已记录的同题来源、目标条目/源码声明和同题路线记忆；这只核对身份，不判断任意数学表述等价。身份匹配且启用目录的运行报告 `knowledgeFunnel`，逐项区分搜索返回、提示候选、实际上下文、模型选择、应用检查和精确原题消费者闭合。旧记录缺失和历史截断保持未知，不能把 helper 完成数当原题完成数，也不将观测归因为收益。

显式 `knowledge build --include-findings --state FILE` 可导入有固定交付和笔记证据的路线记忆，默认排除私有范围。路线记录与已检查定理分开保存，包含精确假设、缺口、证据和重开条件；改任务名不改变数学 scope 摘要，关键词命中不证明假设等价。`knowledge search --include-findings` 与 `knowledge finding` 提供分页回读。M4 每目标最多附带两条匹配路线提示，仍共用原 4 KiB 预算，不能凭旧反驳禁止新探索。

显式 `knowledge enrich` 在完整证明的隔离副本中补采 archived 类型、宇宙参数、语境及实际引用，保存绑定 manifest、record、源码、配置、collector 全文、工具及环境的独立只读 sidecar。`build --accepted-enrichment FILE` 只校验和读取该文件，默认 build/search 不启动 Lean。原 source-header 与独立 elaboration 分开，缺编译器或引用覆盖继续记未知。`knowledge consumers` 反查相同完整源码语境和已知环境中的精确引用，返回 statement-use/proof-use 及类型、前提、语境和证明的分页句柄；引用闭包不提供应用参数或新的证明验收。M4 提示和 search 命中提供该入口，仍受原上下文字节预算约束。

## 局部诊断与观测快照

`check-lean` 优先解析 Lean 的 JSON 消息，保留首个阻塞位置、Lean 报告的假设和目标文本，并兼容旧文本输出。摘要仍有界；`diagnosticArtifacts` 指向绑定源码与环境摘要的原始材料，捕获窗口为每流 4 MiB，`captureComplete` 为 false / null 时不能当作完整输出。检查期间源码变化会明确报错，不复用旧诊断。

对不确定的任务接口，可显式运行 `check-lean --file FILE --type '闭合类型' --context Existing.declaration`，在保存的证明擦除副本及相同作用域中预检。`elaborated` 仅表示类型能够展开，不检查它是否正确表达题意、是否可证或等于原题；未来 helper 尚不存在时也可能失败，因此不将其设为所有计划的强制验收。实际证明、合并后检查和 S3 保持独立。

额外传入 `--expression '实际闭合 Lean 项'` 可核对该项是否具有给定类型。输入按 Lean 项语法解析，拒绝命令注入、洞、sorry 和未解元变量，并记录实际常量引用及诊断身份。这是同一 advisory 应用检查入口，不是独立证明验收。

M5 在 typed helper 的当前源码投影完成后、正式分配和模型调用前执行同一预检。仅完整查询自身的明确类型或解析错误记为 `invalid`，阻塞该接口并给 Lead 精确反馈，不增加模型尝试数或数学失败数。heartbeat、递归深度、内部异常、IO 和未分类错误不判无效，也不缓存。尚不存在的引理依赖、不支持的局部作用域、输入变化和不完整错误记为 `deferred`；工具或环境不可用记为 `unavailable`，均允许原流程继续。当前查询未重建的活动 `set_option`（包括 `maxHeartbeats` / `maxRecDepth`）保守 defer。预检等待期间其他独立任务仍能分配，宿主不将其误报为路线空闲。

预检仅在当前运行进程和同一真实 worker 项目根内复用，最多保留 64 条实际检查结果，绑定合同、依赖、完整源码和配置、实际工具、环境、作用域及调用方原有预算。缓存存取复制结果，避免其他调用方修改缓存记录；命中前及调用方等待后都核对原诊断产物仍存在且摘要匹配，产物损坏或丢失会重新检查。检查点里的结果只用于解释；恢复后重新检查。等待结束会再次核对任务、canonical、worker 角色及归属、路线、模型准入和原预算，过期结果不会派发。`Infinity` 原样保持，不新增解题截止时间。嵌套类型副本直接绑定同一固定依赖根并核对环境身份，不回退到陈旧的 worker package link。

类型展开成功后，只有完整证明擦除投影、模块顺序和映射、查询命令及其余合同和环境输入完全相同时，后续证明体修改才可复用该成功结果。投影摘要和实际副本写入共用同一构造函数；本次原始源码仍形成新的输入摘要并完整核对当前性。原 artifact 保持原样，另用 `projectionReuse` 记录原检查输入、原源码、本次源码和共同投影摘要，不生成新的 Lean 回执。无效类型仍只复用完全相同的原始输入；投影索引随原检查结果一起淘汰，连续证明修改不会增加保留结果数。该复用仅省去重复的 advisory 类型展开，不提供任何证明验收。

每次在途预检另有独立取消信号。计划删除或修订任务、依赖或 canonical 改变、worker 退出以及准入或预算通知使该次派发失效时，宿主取消已过期的检查；无关计划、笔记和活动更新保留仍有效的检查。取消后等待底层检查和清理结束，再释放 worker、移除在途记录并唤醒等待者，`stop()` 也等待该清理。通知时只比较宿主状态，完整源码、工具和 Git 身份仍在返回后重验；没有通知的外部文件变化不会被提前监视或授权复用。取消不发布类型无效结论，也不增加模型尝试或数学失败次数。

每次正常、失败或中断的诊断都会刷新 `.lake/lean-diagnostics-latest.json`，绑定完整输入与原始产物；其与相关 `.lake` 文件均为 advisory，不能当作 Lean 验收回执。发布失败不会覆盖原先的编译或文件错误。

恢复资料通过显式 `run --continuation-manifest FILE` 与原始任务分开。`taskDigest` 继续绑定逐字任务文本，独立 `continuationDigest` 绑定附件索引及每份正文；宿主冻结去重的只读文件，再复制到工人的 `.lake/continuation.json` 及内容目录。四角色的必需输入只添加完整索引和有界读取命令，不重复注入历史证明正文，不覆盖已有必需合同。读取检查摘要、UTF-8、文件类型及精确身份；分页不拆 Unicode surrogate，完整 JSON 行不超过 16000 字节。

恢复在完成结果的提前返回前也检查快照。旧无附件运行不能增加附件，有附件运行可以不再提供原始文件；仍只能读取已绑定快照。盲法声明审阅保持固定声明范围，不接收恢复附件。附件、旧检查与研究假说均为 advisory，M2 与 S3 的验收权限不变。未附加材料的四角色上下文保留逐字相同的消息、指令和编译清单。

`run --continuation-source-run` 在同一运行锁和已准备的证明环境下完成新运行初始化与求解。新取得的无条件回执通过同一对象交给合作运行；合同、环境和源码投影仍匹配时，启动复检复用该回执。JSON 重载不保留进程内归属，独立 `continuation-seed` 后的恢复仍会重新检查。条件证明从其固定 proof 和 seed 源码恢复，保留精确前提版本并在新环境重新检查；声明尚未进入 canonical 时也能接续，前提仍需正式证明和无条件合并验收。

`inspect` 和实验汇总绑定状态 / 结果摘要；`compare --phase check-report` 只读检查保存报告是否过期。重生成报告前将旧内容保存在 `report.json.history/`。同一 runId 继续运行后可以显示最新通过事实，但模型、方法或预算与原对照不一致时仍不计为该对照通过。`protocol` 故障单独展示，尝试次数不能解释为数学失败次数；逐轮变化仍是观测，缺失收据继续标记未知。

## 本轮发现的问题

1. **研究成果缺少必经消费记录。** `lemmaRequests` 原先只随可选 delivery 提示进入上下文，预算不足时可完全省略，而研究任务仍显示 `completed`。现在持久保存提案，Lead 必须处理本轮展示的提案；接到原题 consumer 仍是规划职责。
2. **M3 与 M5 对可执行性的判断不一致。** 绑定的 engineer 下线后，M3 曾认为 goal 仍能推进，M5 却无法分配。现在检查存活工程师及冲突归属，宿主使用 M5 的实际分配条件。不能为避免等待而悄悄转移显式 owner。
3. **声明修复被误当成任务归属。** 一个任务修复其他 helper 后，旧映射可能把该 helper 的引用归到修复者，制造任务假环；固定声明检查通过仍可能无法形成可消费的任务链。现在按真实声明目标归属任务边，辅助声明仍由精确源码引用绑定，修复副作用不再冒充任务接口。
4. **前沿判断没有统一。** 进度报告曾把调查完成直接当成前提闭合，M3 仍检查未证依赖。现在共用闭合判断，避免报告、上下文与恢复跳过真正缺口。
5. **提案交接没有容量边界。** 一千个短小合法提案就可能超过必需上下文硬限制，使 Lead 退出。现在按完整类型分批决策，并检查后续批次调度、来源保留及跨批依赖，避免限制上下文时又丢失研究成果。
6. **暂缓提案没有重新决策入口。** 原先 `deferred` 决定即使缺失前提已经证明，也不会重新进入必需上下文。现在可绑定具体证明任务的精确版本，全部通过后重新派发，并拦截旧响应及重复等待已满足前提。
7. **无关辅助工作掩盖原题停滞。** 即使报告已经识别没有原题消费者的辅助任务，旧运行逻辑仍会把它们当作推迟卡点恢复的理由。现在单独判断原题支持工作，允许 Lead 在独立探索期间处理真实缺口，仍保留已有的恢复去重与证明验收。
8. **数学推理和成果传递受到流程限制。** 旧提示要求 Lead 在研究证明前立即返回任务图，研究交付又固定截短摘要并抑制完整 finding。现在先明确数学路线，再组织任务；完整研究论证按既有预算独立选择，避免交付元数据挤掉可用数学内容。

这些问题说明，局部 Lean 检查通过与端到端证明闭合是不同证据。修复应通过纯调度、交接、引用关系及集成回归验证，不能降低最终验收标准来增加通过数。

当前没有真实解题成功率验证，也没有能力提升百分比。本轮优化未调用真实模型、重启或部署求解任务。
